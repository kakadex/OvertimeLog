# 实现说明（V0.1）

这份文档说明"需求/架构文档 → 代码"的落地情况，以及这一版有意做出的取舍，方便后续接手的人知道哪里是坑。

## 1. 模块与依赖方向

```
:app  →  :core:model, :core:calculation
:core:calculation → :core:model
```

- `core:model`、`core:calculation` 是纯 Kotlin/JVM 模块，没有 Android 依赖，所以计算规则可以用普通 JVM 单测覆盖（`./gradlew :core:calculation:test`）。
- 其余部分（仓库实现、Room、DataStore、Compose）按架构文档 ADR-004 先合并进 `:app`，按包分层；以后要拆 `core:data`、`feature:*` 时，直接按包平移即可。
- 依赖注入用 `di/AppContainer` 手动组装。接口都定义在 `domain/repository`，换实现不影响用例和界面。

## 2. 计算规则（唯一事实源）

`core/calculation/CalculationEngine` 是唯一算法实现，录入页预览与保存落库都调用它。

- 结束时间不晚于开始时间 → 自动加一天，并给"已按次日计算"提示
- 时长 = 结束 − 开始 − 休息扣除
- 小时工资：时薪模式直接取；月薪模式 = 月薪 ÷ 计薪天数 ÷ 日标准工时
- 金额 = 小时工资 × 分钟 ÷ 60 × 倍率，全程 BigDecimal，最后一步 HALF_UP 到分
- 倍率用"千分基点"：1500 = 1.5 倍（与架构文档字段命名一致）
- 手动金额优先于自动金额，但自动值仍会算出来写进规则快照

边界：单条时长 1–1440 分钟；休息 0–1439 分钟且必须小于总时长；备注 ≤ 200 字；手动金额 ≤ 100 万元。校验统一在用例层，界面只做即时提示。

## 3. 数据与快照

- 金额存 `Long` 分，倍率存 `Int` 千分基点，时间存 epoch，展示时按系统时区还原
- 每条记录保存 `rule_snapshot_json`（规则原始值 + 这次算出的时薪/倍率），改规则不会污染历史
- 月度/年度统计全部走 SQL 聚合（`SUM`、`GROUP BY`、`COUNT(DISTINCT)`），不加载全量实体
- 调休获得量来自加班记录的 `comp_time_minutes` 汇总，使用量来自 `comp_time_usages`

详见 [数据库设计](数据库设计.md)。

## 4. 与架构文档的偏差（有意为之）

| 架构文档 | 当前实现 | 原因 |
| --- | --- | --- |
| Hilt | `AppContainer` 手动注入 | 先确保 AGP 9 + Kotlin 2.4 的编译链稳定；依赖都走接口，后续换 Hilt 只改容器 |
| Paging 3 | 按月份区间查询 + `LazyColumn` | 单月数据量有限，Paging 的收益要等"全部月份"大数据量场景；接口 `observeRecords` 已按可分页的形态设计 |
| JUnit 5 | JUnit 4 | 架构文档允许 JUnit4/JUnit5；JUnit4 与 Android 单测环境零配置 |
| Vico / MPAndroidChart | Compose 自绘条形图 | 先避免额外依赖与体积，`ChartSeries` 形态的接口后续再抽 |
| Navigation 类型安全路由 | 字符串路由 + 可选参数 | 类型安全路由需要 kotlinx.serialization 插件；当前只有 9 个路由，字符串足够 |
| CSV 导出 | 已实现（SAF + RFC 4180 + BOM） | 逻辑层已单测；系统文件选择器那一步需要真机/可用模拟器手动确认 |

## 5. 包体积与混淆

- `release` 已开启 R8（`isMinifyEnabled`）与资源裁剪（`isShrinkResources`），实测 13.3 MB → 1.8 MB
- **应急开关**：`./gradlew :app:assembleRelease -PdisableR8=true` 可在不改代码的情况下关掉压缩（体积回到 9 MB 左右），用来判断"问题是不是 R8 裁错类导致的"
- **keep 规则基线**写在 `app/proguard-rules.pro`：只保留通用属性（注解、内部类、枚举 values/valueOf、Parcelable CREATOR、行号），不盲目 keep 整包
- R8 会把"只在反射里用到的类"当成无用代码删掉。以后接入 kotlinx.serialization（备份 JSON）、Hilt（反射注入）或任何 `Class.forName` 逻辑时，**必须同步补 keep 规则**，并重跑发布冒烟
- **发布冒烟脚本**：`scripts/smoke-release.ps1`，自动构建 → 测试签名 → 干净安装 → 走"配规则 → 记一笔 → 保存" → 断言条数与金额（¥258.62） → 检查日志无崩溃。每次改 R8 规则、升级依赖、改数据库都要跑
- 冒烟脚本用 debug 证书签名，仅为本地/CI 验证，**不能当发布包用**
- `debug` 包 13 MB 属于正常现象，不要拿它判断发布体积
- release 目前还没有签名配置（产物是 `app-release-unsigned.apk`），正式发布前要加 `signing.properties`（不入库）并用发布证书签名

### 为什么当前可以放心开 R8

这个版本没有任何"运行期按名字找类"的用法：Room 用 KSP 编译期生成 DAO 实现，Compose 编译期生成，Navigation 用字符串路由，DataStore 用 Preferences（无 protobuf 反射），没有 Gson/Moshi/kotlinx.serialization。因此 R8 只做"删死代码"，不改变存活代码的行为。上面那条"以后接入反射要补规则"就是给后续版本留的护栏。

## 6. 已知限制

- 模拟器（无窗口模式）上系统文件选择器的"保存"按钮点击不稳定，导出流程需要在真机上再确认一次
- CSV 导出目前只有"全部记录"，按月导出的入口还没做（`ExportCsvUseCase` 已支持传入日期区间，补界面即可）
- 年度统计的月份聚合用 SQLite `strftime` 从"天序号"换算，年份范围外（<1970）的数据不适用
- 清除数据只清记录和调休，不重置薪资规则与偏好设置（避免误删配置）
- 还没有数据库迁移：当前 `version = 1`，第一次改表前要先把 `exportSchema` 打开并提交 schema
- release 包不是 debuggable，`run-as` 读不到私有数据库；冒烟脚本以界面断言（值来自数据库）为准，DB 直连只在 debug 包上可用
- 底部导航的文字中心落在屏幕最下方一段触摸死区，自动化脚本要点"可点击父节点"的中心（脚本里已处理）

## 8. 检查更新（V1.0.2）

- 只读两个公开接口：Gitee 的 `releases/latest` 为主，失败自动回落 GitHub 同名接口；两边都失败只给一句中文提示，不影响记录功能
- 用 `HttpURLConnection` + Android 内置 `org.json` 解析，不引第三方网络库；连接与读取各 6 秒超时，断网时不会拖住启动
- 版本比较放在 `domain/model/AppVersion`（纯 Kotlin，与网络无关）：解析 `v1.0.2` / `1.0.2` / `1.0.2-beta`，逐段比较整数，远端不比本机新就按"已是最新"处理，可直接单测
- 检查结果只存一份（`UpdateChecker` 的 StateFlow），设置页手动检查与启动静默检查共用，切页面不会丢结果；`Mutex` 防止连点发两次请求
- 启动检查受 `update_check_on_startup` 开关控制；失败标记 `silent`，设置页不显示，避免用户没点却看到报错
- 首页只在"发现新版本"时显示一条提示（可"去下载"/"忽略"），不弹对话框；"忽略"只保留到本次进程结束
- 发布页链接由 `ReleaseChannels` 统一拼装，换仓库只改一处；打开链接走系统浏览器，不内置 WebView
